# ELITE Spaces v1.1 design: fixed schedules, daily goals, alert end, missed-day notice

Oct 28, 2026. Source: Stephen's answers (docs/decisions.md S-1..S-15) and Justin's decisions on them.
This is the build plan for v1.1. Builders follow it, critics judge against it. Where it says "D-4x",
that rule goes into docs/decisions.md word for word in step 0.

What changes, in one line each:
- **Fixed schedules (S-3).** A director publishes schedules ("Mornings MWF 9:00-12:00") for a period. A parent
  enrolls a student in one whole schedule; the student attends every listed date. No per-day slots, no student requests.
- **Date changes.** A director can skip, add or move one date of one schedule. Closures still cancel a whole day at the location.
- **No location check (S-5).** A scan of today's code is presence. The app never asks for the phone's location.
- **Daily goals (S-8).** After each check-in the student is asked for up to 3 goals for the day. Staff see them
  beside the ratings; parents see them in the posted note.
- **End an alert early (S-11).** Directors (own location) and HQ end an emergency alert; it unpins and shows "Ended".
- **Missed-day notice (S-12).** A scheduled day that passes with no check-in at all tells each active parent once.
- **Not built:** combined feed (S-10), call button (S-13), audit log in exports (S-14), more notification settings (S-15).

## 1. Data model

### 1.0 Two ground rules for the schema

1. **No `ALTER TABLE` in v1.1.** `src/db.js` re-runs every schema file on every open, so an
   `ALTER TABLE ... ADD COLUMN` throws "duplicate column name" the second time the app starts. Every new
   field goes in a new side table (`CREATE TABLE IF NOT EXISTS`). Why: no change to db.js and no migration runner needed.
   CLAUDE.md's ownership table is corrected to say "new tables and indexes only" (D-55).
2. **The core tables keep their columns.** `CREATE TABLE IF NOT EXISTS` never changes an existing
   database, so a core column change would only reach fresh databases. v1.1 reuses existing columns with a
   documented new meaning instead (below).

### 1.1 The schedule is the existing `sessions` row (D-41)

| Concept | Where it lives | Notes |
|---|---|---|
| Schedule | `sessions` row (unchanged columns) | name, `weekdays` (the fixed days), `start_time`/`end_time`, `capacity` (seats per meeting date), `status` |
| Period (a month or a semester) | `terms` row | Each schedule belongs to one term, and the term's start and end dates are the schedule's start and end dates. A director makes a term per month or per semester, whichever they want. **Periods at one location never overlap** (D-56): a location runs semesters or months over any stretch of dates, not both at once. |
| Single-date change | new `session_dates` (030) | skip / add / move, per schedule |
| Whole-day cancel | `closures` (unchanged) | location-wide, every schedule |

Why terms are the period: the term machinery already exists and is tested: closures must sit inside a term,
shortening a term notifies families (D-33), the attendance "Term" view and range shortcuts (AT-2), and the
announcement session picker (D-40). Giving each schedule its own date columns would duplicate all of that.
A schedule's own dates are its term's dates. The UI calls a term a **Period**, with the hint "a month or a semester".
The code and the database keep the name `term`.

### 1.2 Per-module schema changes

**schema/000_core.sql (foundation): comments only, no column or constraint changes.**
- `locations.lat`, `lng`, `geofence_m`: "Unused since v1.1 (S-5, D-49). Kept so existing databases still open.
  New locations store 0, 0 and 150."
- `sessions`: replace "Each (session, weekday) pair is one weekly slot; capacity applies per slot" with
  "A session is a **schedule** (D-41): fixed weekdays and times for the whole of its term (its period, a month or a
  semester). `capacity` is seats per meeting date. Single-date changes are in `session_dates` (030_sessions.sql)."
- `enrollments.weekday`: "**0 = the whole schedule** (v1.1, D-42). 1-7 = a v1 per-weekday row, which counts only on
  that weekday. Nothing writes 1-7 after v1.1." The comment "Recurring enrollment in one weekly slot" becomes
  "Enrollment in one schedule for the rest of its period (EN-1)."
- `waitlist.weekday`: same: 0 = the whole schedule.
- `visits.weekday`: "The ISO weekday of local_date. Informational only." Check-in still writes it.
- `enrollments.source` keeps `'request'` in its CHECK so v1 rows stay valid. v1.1 writes only `parent`, `waitlist`
  and `staff` (the migration uses `staff`).

**schema/030_sessions.sql (sessions): one new table.**
```sql
-- v1.1 (D-46): one schedule's own date changes. 'skip' cancels one meeting date of
-- this schedule only. 'add' makes an extra meeting date, at the times the schedule
-- has that day (D-34). A move is a skip and an add written together; the add
-- carries moved_from. Closures stay location-wide (closures table).
-- Only today or later can be changed, so past dates never change.
CREATE TABLE IF NOT EXISTS session_dates (
  id          INTEGER PRIMARY KEY,
  session_id  INTEGER NOT NULL REFERENCES sessions(id),
  date        TEXT NOT NULL,                 -- 'YYYY-MM-DD', location-local
  kind        TEXT NOT NULL CHECK (kind IN ('skip','add')),
  moved_from  TEXT,                          -- on an 'add' made by a move: the date it replaces
  reason      TEXT,                          -- shown to families, up to 120 chars
  created_by  INTEGER REFERENCES users(id),
  created_at  INTEGER NOT NULL,
  UNIQUE (session_id, date)
);
CREATE INDEX IF NOT EXISTS session_dates_by_date ON session_dates(date);
```
Undoing a change deletes its row (an audit row records it). `session_times` (D-34) stays as it is.

**schema/040_enrollment.sql (enrollment): no new tables.**
- `enrollment_requests` stays, with the comment "Retired in v1.1 (D-48). Kept as history. Nothing writes it."
  Why: dropping a table isn't additive, and old Inbox items point at its rows.
- The existing indexes (`enrollment_seats`, `enrollment_waitlist_line`) serve `weekday = 0` rows as they are.
- The `enrollment_status_log` trigger is unchanged (D-26).

**schema/050_membership.sql: no change.**

**schema/060_announcements.sql (announcements): one new table.**
```sql
-- S-11 / D-52: an emergency alert ended early. One row per ended alert; it is no
-- longer pinned, and everyone who can see it sees "Ended" with this time.
CREATE TABLE IF NOT EXISTS announcement_ends (
  announcement_id INTEGER PRIMARY KEY REFERENCES announcements(id),
  ended_by        INTEGER NOT NULL REFERENCES users(id),
  ended_at        INTEGER NOT NULL
);
```

**schema/070_notes.sql (notes): two new tables.**
```sql
-- S-8 / D-50: a student's goals for one location-local day. No row = not answered yet.
-- 'set' has 1-3 rows in daily_goals; 'skipped' has none.
CREATE TABLE IF NOT EXISTS daily_goal_days (
  student_id  INTEGER NOT NULL REFERENCES users(id),
  local_date  TEXT NOT NULL,
  location_id INTEGER NOT NULL REFERENCES locations(id),
  status      TEXT NOT NULL CHECK (status IN ('set','skipped')),
  updated_at  INTEGER NOT NULL,
  PRIMARY KEY (student_id, local_date)
);
CREATE TABLE IF NOT EXISTS daily_goals (
  student_id  INTEGER NOT NULL,
  local_date  TEXT NOT NULL,
  position    INTEGER NOT NULL CHECK (position BETWEEN 1 AND 3),
  subject     TEXT NOT NULL CHECK (subject IN ('math','english','science','history','language','art','test_prep','other')),
  text        TEXT NOT NULL,                   -- 1-280 characters
  PRIMARY KEY (student_id, local_date, position),
  FOREIGN KEY (student_id, local_date) REFERENCES daily_goal_days(student_id, local_date)
);
```

**schema/080_attendance.sql (attendance): one new table.** (Attendance stops being "stores nothing".)
```sql
-- S-12 / D-53: one missed-day notice per student per location-local date, so the
-- job never sends twice. `sessions` lists what was missed, for the notice and Hours.
CREATE TABLE IF NOT EXISTS missed_day_notices (
  id          INTEGER PRIMARY KEY,
  student_id  INTEGER NOT NULL REFERENCES users(id),
  location_id INTEGER NOT NULL REFERENCES locations(id),
  local_date  TEXT NOT NULL,
  sessions    TEXT NOT NULL,                   -- JSON [{session_id, name, start_time, end_time}]
  sent_at     INTEGER NOT NULL,
  notified    INTEGER NOT NULL DEFAULT 1 CHECK (notified IN (0,1)), -- 0 = seed placeholder: blocks the job, nobody was told
  UNIQUE (student_id, local_date)
);
```
Rows with `notified = 0` are written only by the attendance seed (5.3) so a freshly seeded server doesn't flood
families. Hours shows "Parents notified" only for `notified = 1`, and `GET /missed/:id` answers 404 for a placeholder.

**schema/010_accounts.sql, 020_checkin.sql: no change** (020's comment drops the radius sentence; there are still no coordinate columns).

### 1.3 The meeting-date helper (sessions owns it, everyone reads it)

`src/modules/sessions/dates.js` is a read-only helper the sessions module exports on purpose, like `times.js`.
Today six places decide whether a student meets on a date with `e.weekday = weekdayOfDate(date)`:
checkin `slotsOn`, notes `slotEnds`, attendance `absences`, `coversSession` and `visitEnd`, enrollment `schedule` and
`visitEnd`, and sessions `studentsMeetingOn` and `studentsCutByTerm`. All of them switch to this helper. Why: with
moved and added dates, "meets on this weekday" is wrong, and one shared definition keeps Schedule, check-in,
Hours and the missed-day notice in agreement.

```js
// Every schedule's date changes: session id -> Map(date -> { kind, moved_from, reason }).
overrides(ctx, sessionIds = null)
// Does the schedule meet on `date`? `s` needs weekdays, term_start, term_end.
// In its term, and either (on one of its weekdays and not skipped) or added. Closures are NOT applied here:
// callers apply them as they do today, so Schedule can still show "Center closed".
meets(s, ov, date)
// Its meeting dates in [from, to], oldest first, closures not removed.
datesOf(s, ov, from, to)
// Does this enrollment count on `date`? weekday 0 = every meeting date; 1-7 = a v1 row, that weekday only.
counts(e, date)
// How many days a week the schedule meets: its weekday count. Date changes don't change it.
daysPerWeek(s)
```
A change outside its schedule's term is ignored (a shortened term simply drops it).

### 1.4 Moving v1 per-weekday enrollments to whole-schedule enrollments (D-54, MIG-1)

**Where it lives and when it runs.** `src/migrate-v1.1.js` (foundation) exports `module.exports = { migrate }`, where
`migrate(ctx)` returns a report `{ ran: bool, students: [{ student_id, name, kept, paused_over_cap, dropped: [names],
waits_removed: [names] }], capacity_raised: [{ session_id, name, from, to }], requests_declined, overlapping_terms: [...] }`.
`createApp()` in `src/app.js` calls it **on every open, right after the schema files run and before any job**, and
stores the report on `ctx.migration`. So `server.js` (and with it Render's `startCommand: node server.js` in
render.yaml) migrates a hosted database on its first v1.1 start, with no manual step. `scripts/migrate-v1.1.js` is a
CLI wrapper only: it opens `ELITE_DB` through `createApp()` (which migrates) and prints `ctx.migration`.
`docs/deploy.md` gets one paragraph: "Upgrading from v1: the first start moves v1 enrollments to whole schedules and
writes one `enrollment.migrate_v1_1` audit row; read it before telling families." CLAUDE.md's ownership table lists
`src/migrate-v1.1.js` and `scripts/migrate-v1.1.js` under foundation.

**Idempotent.** It runs in one transaction and returns `{ ran: false }` at once when no live row has `weekday <> 0`
(no live enrollment `status IN ('active','paused')` and no `waiting` waitlist row). Fresh and seeded databases
therefore pay one cheap query per open. A second run finds no v1 rows (step 2 ended them) and does nothing.

**Steps** (`now` = `ctx.clock.now()`; "overlap" = the D-43 term-date overlap):

1. Group live v1 enrollment rows (`status IN ('active','paused')`, `weekday <> 0`) by (student, session). Leave
   rows whose term has ended as they are (they are history).
2. End every row in every group: `status = 'dropped'`, `ended_at = now` (D-26 (4)). Their past dates keep counting
   on their own weekday through `dates.counts()`, so Hours and absences before the migration don't change.
3. **One schedule per period, chosen without any automatic switch later.** For each student, among groups whose
   terms overlap, keep one: the one with the most v1 days, then the oldest `created_at`. The other groups are
   **dropped outright**: no new enrollment row and **no waitlist row of any kind** for them. They are named in the
   family's notice (step 8). Why: a live waiting spot for them would, under D-44, switch the student out of the kept
   schedule the first time a seat opened, a switch no parent chose.
4. **The cap never unseats; it pauses.** For each kept group, insert one whole-schedule row (`weekday = 0`,
   `source = 'staff'`, `created_by = NULL`, `created_at = now`). It is `active` if any row in the group was active and
   the schedule's `daysPerWeek <= weekly_cap`. Otherwise it is `paused`: either the group was already paused
   (membership lapse), or the days don't fit the cap. A cap misfit is the D-16a "kept over the cap" state: membership
   `restore` brings it back as soon as staff raise the cap to fit. The row is inserted `active` and then updated to
   `paused`, so the D-26 status-log trigger stamps the pause and attendance reads its dates as Paused, never absent.
   It is never a waitlist row.
5. **Capacity never unseats; it grows.** After step 4, for each schedule whose active `weekday = 0` count is above
   its `capacity`, set `capacity` to that count (at most 1,000, the D-10a ceiling; a schedule over 1,000 keeps every
   student and is reported). Every raise goes in the report and the audit row, and each director of that location
   (and HQ) gets one `schedule_migrated` staff notice (`ref_type 'session'`): "Mornings MWF now has 26 seats (was 24) so every enrolled
   student kept a place. Lower it only after families leave."
6. **v1 waiting rows.** Waiting v1 rows become one `weekday = 0` waiting row per (student, session), keeping the
   earliest `created_at` and the highest `priority`; the v1 rows are set `removed` with `resolved_at = now`. **But** a
   waiting spot for a schedule that overlaps the schedule the student now holds (step 3/4) is not carried over: it
   is set `removed` and named in the notice. Why: same as step 3, a v1 wait meant "add this day", and a v1.1
   promotion would mean "replace my schedule". Waits for schedules in non-overlapping periods, and waits of students
   who hold nothing overlapping, carry over.
7. `enrollment_requests` that are still pending become `declined`, with the reason "Students no longer request
   sessions. A parent picks the schedule." No notice is sent.
8. Each affected family gets one `schedule_migrated` notice (`ref_type 'enrollment'`, to the student and active
   parents) that names, per student: the schedule kept; "paused because Mornings MWF meets 3 days a week and Anh's
   membership allows 2; staff can raise the limit"; every dropped schedule ("Leo no longer holds Quiet Room TTh.
   Students now keep one schedule per period; you can switch to it in Schedule."); and every removed waiting spot.
9. One audit row `enrollment.migrate_v1_1` holds the whole report: counts, **every student unseated or paused with
   the reason**, every dropped schedule and removed waiting spot, every capacity raise, and any pairs of v1 terms
   at one location that overlap (D-56 isn't applied backward; they are left for the director to fix).

Nothing in v1.1 counts a live `weekday <> 0` row for seats, the cap, D-43 or `held_days` (they count `weekday = 0`
only), which is exactly why the migration runs at every start instead of "once, by hand".

### 2.2 New rules (add to docs/decisions.md under "v1.1 rules, from Stephen's answers and Justin's decisions (Oct 28, 2026)")

| # | Rule |
|---|---|
| D-41 | **A schedule is a session row in a term** (S-3). It has a name, fixed weekdays, one 2-3 hour time, and seats per meeting date. Its period is its term: a month or a semester, as the director sets the term. The screens say "Schedule" and "Period". The code keeps `session` and `term`. |
| D-42 | **One enrollment row per schedule.** An enrollment or waitlist row with `weekday = 0` covers every meeting date of its schedule. Rows with 1-7 are v1 history and count only on their weekday. |
| D-43 | **One schedule per period, and the cap is days a week.** A student holds at most one live (active or paused) enrollment among schedules whose terms overlap (`a.start <= b.end AND b.start <= a.end`). Enrolling in another overlapping schedule is a **switch**: the old enrollment ends (dropped, D-26), its seat goes to its waitlist, and one notice tells the family about both. Enrollment is blocked when the schedule's `daysPerWeek` is more than the membership's `weekly_cap`. **Membership dates are checked against the schedule, not today:** let F be the schedule's first meeting date on or after today (D-47, closures removed). The membership must be `active` and `start_date <= F <= expires_on`. So a renewal starting Nov 1 can enroll on Oct 28 in a November period whose first date is Nov 2, and a membership ending Dec 31 can't enroll in a January period. Block codes and messages: `membership_inactive` "Leo's membership isn't active. Ask the front desk."; `membership_not_started` "Leo's membership starts Nov 1, after this schedule's next date (Oct 30). Choose a schedule that starts on or after Nov 1."; `membership_ends_first` "Leo's membership ends Dec 31, before January Mornings MWF starts (Jan 4). Renew it first."; `membership_expired` (already past) "Leo's membership ended Sep 30. Renew it first."; `no_membership` "Leo has no membership yet. Ask the front desk." A membership that ends partway through the period is allowed: the schedule pauses when it expires (MB-5). Schedules in periods that don't overlap (Fall, then January) can be held together. Why: Justin said a family picks ONE schedule per period, and then the cap check is a single comparison. |
| D-44 | **The waitlist is per schedule.** It is first come, first served, with renewals at the front (priority 1, D-16). When a seat opens, the earliest waiting student is enrolled if their membership passes the D-43 date check (against the schedule's first meeting date on or after the promotion day) and the schedule's days fit their cap. Anyone ahead who fails a check is skipped but keeps their place. A promotion is a switch if the student holds an overlapping schedule. Taking a seat removes the student's other waiting spots in overlapping periods, and the notice says so. A family can wait for a schedule while keeping its current one. |
| D-45 | **Days are fixed once families commit.** A schedule's weekdays can change only while it has no live enrollments and no one waiting. After that, the name, times (from today on, D-34) and seats can still change, and for single weeks the director uses date changes (D-46). To change days for the rest of the period, cancel the schedule and publish a new one. Why: families committed to that calendar, and the cap was checked against it. |
| D-46 | **Date changes, per schedule.** A director (own location; HQ any) can **skip** a meeting date, **add** a date that isn't one, or **move** a date (a skip and an add in one step, with one notice). The rules: dates today or later, by the location's date; inside the schedule's term; an added date isn't a closure day and uses the times the schedule has that day; a skipped date can't already have a visit for that schedule. Undo deletes the change, also today or later only. Every change notifies the students with an active or paused enrollment in the schedule, and their active parents, once. The weekly cap isn't checked against date changes: a week with an extra date is the director's choice. |
| D-47 | **What "meets on a date" means.** A schedule meets on date d when d is inside its term and either (d's weekday is one of its weekdays and d isn't skipped) or d is added. A closure at the location then cancels d for every schedule. Every module reads this from `sessions/dates.js` (D-26 (6)). |
| D-48 | **Only parents enroll** (S-3, EN-2). Students can't request schedules any more. The request routes, job, screens and notices are removed. `enrollment_requests` stays as read-only history, and old request items in the Inbox open Schedule. |
| D-49 | **No location check** (S-5). A scan of today's code at the student's home location counts as being there. The app never calls the browser's geolocation. The scan route ignores any `lat` and `lng` it is sent and never stores them. Location settings no longer show or accept a check-in radius, and new locations don't ask for coordinates (stored as 0, 0, 150). |
| D-50 | **Daily goals** (S-8). Each student has one goal record per location-local day: not answered (no row), set (1-3 goals), or skipped. A goal is a subject (Math, English, Science, History, Language, Art, Test prep or Other) plus 1-280 characters of text. Each subject offers three example goals the student can tap to start from. The student is asked after every check-in until they answer for that day. They can set or edit goals only on that day, and only after a check-in that day at their home location. Skip is allowed only while not answered; once goals are set they can be edited but not skipped. Staff see each student's goals and status on Daily notes. Parents see the goals inside the posted note only. Students see their own goals for today but still not notes (D-2). The subject list and examples are fixed in code (HQ can't edit them in v1.1). |
| D-51 | **Staff reply to goals in the note's comment** (DN-3). There is no separate reply thread on goals. Why: parents read one place, and staff write the note with the goals in front of them. |
| D-52 | **Ending an emergency alert early** (S-11). HQ can end any active alert. A director can end an active alert whose only location is their own, whoever sent it. An alert sent to several locations can be ended only by HQ, because ending it is network-wide. An ended alert is no longer pinned on Home or News. Everyone who can see it sees "Ended" with the time and who ended it (HQ shows as ELITE HQ). Its recipients get one normal-priority notice ("All clear: ... has ended"), sent even to people who muted announcements, because the alert itself ignored mute. An end can't be undone, and only alerts within their 24 hours can be ended. |
| D-53 | **Missed-day notice** (S-12). A student's day is missed when they had at least one scheduled date that day (D-47: not a closure or skipped date), each of those dates would count as absent (D-15: enrollment live and not paused when it began, membership valid), and there is no visit at all that day at their home location. Once the last of those dates has been over for 30 minutes (time for staff to fix a forgotten check-in), each active parent gets one `missed_day` notice for that student and date. A staff check-in made later doesn't take it back. The job only looks at each location's today and yesterday, so turning the feature on or seeding data never sends notices for old days, and the attendance seed writes placeholder rows (`notified = 0`) for its today and yesterday so a freshly seeded server sends only the one intended demo notice (5.3). A day where the student came to one session but not another is not "missed": it shows as Absent in Hours with no notice. |
| D-54 | **v1 enrollments move to whole schedules** at every app start (createApp), idempotently, as described in section 1.4. The migration never unseats a student over capacity (the seat count grows) or over the cap (the schedule is kept paused, D-16a), and never leaves a live waiting spot that could switch a student out of the schedule they kept. Its audit row lists every student affected. |
| D-55 | **Schema files: new tables and indexes only.** There is no `ALTER TABLE` (db.js re-runs every schema file on each open). New fields go in side tables. |
| D-56 | **Periods at one location don't overlap.** Creating or editing a term whose dates overlap another term at the same location is refused: 409 `term_overlaps` "Fall 2026 already covers Nov 2 - Nov 30. Periods at one location can't overlap. Use months or a semester for these dates, not both." Terms that already overlap in a v1 database are left as they are (the migration lists them) and must be fixed before either is edited. Why: with overlapping periods, "Switch to this" on a November schedule would end a whole Fall semester enrollment, and attendance's Period view, prev/next and "This term" (`termIndex`) pick one term per date. With no overlap, D-43's switch only ever replaces a schedule in the same stretch of dates, and attendance stays as it is. A location can still use months in one part of the year and semesters in another. |

## 3. Per module: API, jobs, notifications, screens

Routes are under `/api/<module>`. "409 code" means `{ error: code, message }` as today.
Every new route enforces scope (NF-1) and gets a family-scope test and a staff-other-location test.

### 3.8 attendance (missed-day notice, D-53)

**Service:** `absences()`, `coversSession()` and `visitEnd()` step through `dates.datesOf()` and filter with
`dates.counts(e, d)` instead of stepping 7 days from a weekday. A new `missedDays(ctx, location, date, now)` returns
the students whose every dated occurrence that day is absent, whose last occurrence ended at least 30 minutes ago,
and who have no visit that day at that location.

**Routes:** the existing paths stay. Reports label sessions as schedules (AT-4). One new route:
`GET /missed/:id` (parent, own linked student only; 403 otherwise) returns `{ student_id, local_date, sessions }`,
so a missed-day Inbox item can open the right student and week.

**Job (new): `missed-day`.** For each active location, for its today and yesterday: `missedDays()`, then
`INSERT OR IGNORE INTO missed_day_notices`. Only when a row was inserted, it sends `notify.send(parentsOf(student))`.
**Notification `missed_day`** (`ref_type 'missed_day'`, `ref_id` = the notice id): "Leo didn't check in today" /
"Afternoons MWF, Mon, Nov 2, 1:00-4:00 PM at Irvine. No check-in was recorded. If Leo was there, the front desk can
add the visit." The wording is neutral, with no penalty (EN-7).

**Screens**
- **Hours:** the view accepts `#/hours/<studentId>/<date>` (opens that student's week holding the date) and
  `#/hours/missed/<noticeId>`. The attendance view registers `App.inboxLink('missed_day', n => 'hours/missed/' + n.ref_id)`
  (synchronous, like every inboxLink route). On `#/hours/missed/<id>` the Hours view calls `GET /api/attendance/missed/:id`
  and then replaces the hash with `#/hours/<student_id>/<local_date>` (`location.replace`, so Back doesn't loop); on
  403 or 404 it shows the plain Hours page with the toast "That notice isn't available." An absence row on a day with
  a `notified = 1` notice shows "Parents notified" in muted text.
- **Reports:** "Session" filter label becomes "Schedule".

## 6. Risks and edge cases

| Case | Decision |
|---|---|
| **Enrolling partway through a period** | Allowed while the schedule has a meeting date today or later; otherwise 409 `no_dates_left`, and the catalog hides it. Dates that began before the enrollment are never absent, and no missed-day notice is sent for them (absences already skip `start < created_at`). The catalog says "9 of 21 dates left". |
| **Enrolling during today's date** | Same as v1: if check-in is still open the student can scan in. Today's date counts only if they come (enrollment `schedule()` "began" rule). |
| **Drop, then waitlist promotion** | The drop and the promotion happen in one transaction (NF-3). The promoted student's overlapping schedule ends (a switch) and frees a seat there, and that line is promoted in the same transaction, which can cascade. The cascade ends because each step removes a waiting row. Ineligible students ahead are skipped but keep their place (D-44). |
| **Two parents act at once** | Writes are synchronous in `tx()`. The second request sees the first one's result: a second enroll in an overlapping schedule is just another switch, and the last one wins. Both get notices. |
| **Waiting for two schedules in one period** | Allowed. The first one to seat the student removes the other spot (D-44), and the notice says so. |
| **Editing a schedule after enrollment** | Days are locked (D-45, 409 `days_locked`). A time change applies from today on (D-34) with a `session_changed` notice. Seats can go up (promotes at once) but not below the enrolled count. Cancelling ends everyone's enrollment and waiting spot, with a notice. |
| **Membership expiring mid-period** | The next day (by the location's date) the schedule is paused, not deleted (MB-5). Its dates after that are "Paused", never absent, and get no missed-day notice. On renewal it comes back if the seat is free and the days fit the cap; otherwise the student goes to the front of the waitlist, or it stays paused because of the cap (D-16a). Enrolling is allowed while the membership is still valid on the schedule's first remaining date, even if it ends before the period does (D-43). |
| **Cap lowered below a held schedule** | Refused (D-27, changed). A parent switches to a schedule with fewer days, or drops, first. |
| **A date moved after families enrolled** | Every student with an active or paused enrollment in that schedule, and their parents, gets one notice per change (move = one notice, not two). Waitlisted families aren't told (they don't attend yet). Undo notifies again. Today's date can't be skipped or moved once someone has a visit for it (409 `date_has_visits`), so no visit is ever left pointing at a cancelled date. |
| **An added date that later becomes a closure** | The closure wins (D-47) and its own notice goes out. The added date shows as "Center closed". |
| **A period shortened past an added date** | The change is outside the term, so `dates.js` ignores it. D-33's notice already tells families. |
| **A moved date over the weekly cap** | Not checked (D-46). The cap is about the schedule's pattern; a holiday week's extra date is the director's call. |
| **Missed-day timing** | The 30-minute grace and the today-plus-yesterday window are measured in the location's own zone (NF-4). The job runs every 30 s and is idempotent through the unique (student, date) key. If the server is down more than a day, those days are skipped on purpose (no late flood). A staff check-in after the notice doesn't send a correction; Hours shows the visit. |
| **Missed-day with two schedules in a day** | Only possible with v1 rows or non-overlapping periods meeting the same day (not possible by D-43). One notice per student per date lists every missed schedule. Attending any part of the day means no notice. |
| **Goals before check-in, or for another day** | Refused (`no_visit_today`). Goals belong to a day at the center. |
| **A student checks out and back in** | Not asked again if the day is already answered. Asked again if they ignored the prompt the first time (the day is still unanswered). |
| **Goals and note timing** | Parents see goals only inside the posted note. Goals are read live, so an edit later that day shows in the note. Staff can't edit goals. |
| **Ending an alert sent to several locations** | HQ only (D-52). A director sees the alert without End. Ended alerts are never re-pinned. A pop-up already on a phone stays until tapped, and "I have read this" still counts as a read (AN-6). |
| **Old Inbox items** | `enrollment_request` items open Schedule. `session_day_removed` items still open Schedule through the `session` link. |
| **Legacy v1 rows in a database** | The migration (1.4) runs inside `createApp()` on every start, so a hosted database (Render runs `node server.js`) is migrated on its first v1.1 start with no manual step. It must run: seat counts (`seatsTaken`, `capacity_below_enrolled`, restore's "taken"), the D-43 one-schedule check and `held_days` count only `weekday = 0` rows, so a live v1 row would be invisible to capacity and the cap. `dates.counts()` reads 1-7 rows only for history (Hours and absences of dropped v1 rows). |
| **Overlapping periods** | Refused for new or edited terms (D-56, 409 `term_overlaps`). v1 terms that already overlap are listed in the migration audit row; until the director fixes them, D-43 still compares real dates (a switch can end the longer one) and attendance shows the first term by start date, as today. |
| **Enrolling ahead of a membership start, or past its end** | Checked against the schedule's first meeting date on or after today (D-43): a renewal starting Nov 1 can enroll on Oct 28 in a period starting Nov 2 but not in the running Fall schedule (`membership_not_started`); a membership ending Dec 31 can't enroll in January (`membership_ends_first`). Waitlist promotions use the same check on the promotion day. |
| **Freshly seeded server** | The attendance seed's placeholders (5.3) stop the missed-day job from notifying for the seed's today and yesterday, so Leo's is the only notice. |
| **Scoped test runs** | `dates.js` lives in sessions but is required as a file, so it loads with or without the sessions module (the same way times.js works today). |

## 7. Changes after review (Oct 28, 2026)

A fresh critic found nine gaps. Each was fixed in the sections named; no code was changed.

1. **Migration could trigger switches nobody chose** (1.4 steps 3 and 6, D-54). A student's extra overlapping v1
   schedules are now dropped outright, with no waitlist row of any kind, and named in `schedule_migrated` ("Leo no
   longer holds Quiet Room TTh..."). v1 waiting spots for a schedule overlapping the kept one are set `removed` and
   named too, for the same reason. MIG-1 flow 6 proves no switch happens when a seat opens later.
2. **Migration unseated students over the cap or capacity** (1.4 steps 4-5, 9; D-16a row). A cap misfit is kept as a
   whole-schedule enrollment set to `paused` (the D-16a kept-over-the-cap state, stamped in the status log, restored
   when staff raise the cap), never a waitlist row. Capacity overflow raises the schedule's seats to fit and tells the
   location's directors. The audit row lists every student paused or dropped, with the reason.
3. **Nothing ran the migration on Render** (1.4, section 6). `migrate(ctx)` now runs inside `createApp()` on every open,
   after the schema and before jobs, so `node server.js` (render.yaml's start command) migrates a hosted database on its
   first v1.1 start. `docs/deploy.md` gets an upgrade note. The false "nothing breaks if it never runs" claim is deleted
   and replaced with why it must run.
4. **Overlapping periods were undecided** (new D-56, 1.1, 3.1 terms routes, SC-3, section 6). Periods at one location may
   not overlap: `POST/PUT /terms` answer 409 `term_overlaps`. D-43 switches and attendance's term navigation stay as they
   are. Overlapping v1 terms are left alone and listed in the migration report.
5. **Missed-day Inbox link couldn't be built** (3.8, 3.9). `App.inboxLink('missed_day', n => 'hours/missed/' + n.ref_id)`;
   the Hours view resolves the id through `GET /api/attendance/missed/:id` and replaces the hash with
   `#/hours/<studentId>/<date>`. `missed_day` is added to the core.test.js inboxLink map test.
6. **Fresh seed flooded families with missed-day notices** (1.2 `missed_day_notices.notified`, 5.3 attendance seed, D-53,
   section 6). The attendance seed writes `notified = 0` placeholders for every seeded student scheduled on the seed's
   today and yesterday, after Leo's real notice, so Leo's is the only one. Hours and `GET /missed/:id` ignore placeholders.
7. **Existing foundation tests broke with no owner** (5.1). Step 3 now lists each one to rewrite: the MB-5/EN-7/AT-2
   flow for whole-schedule pause and restore, the one-weekday `enroll()` flows, the NF-1 Home-card list (drop
   `/api/enrollment/requests`, add `/api/notes/goals/today`), `north()`, the integration mutations and the core Inbox

   coverage demands its test and mutations. Interface: `src/migrate-v1.1.js` exports `migrate(ctx)` returning a report;
   `scripts/migrate-v1.1.js` is a CLI wrapper. Tests cover overlap, cap, capacity, waiting spots, idempotence and the

9. **Membership dates checked only against today** (D-43, D-44, 3.2 catalog, EN-4, section 6). The membership must be
   active and valid on the schedule's first meeting date on or after today. Families can enroll ahead in a period that
   starts after their renewal begins, and can't enroll in a period that starts after their membership ends. Block
   messages are named for each case: `membership_not_started`, `membership_ends_first` (new), `membership_expired`,
   `membership_inactive` and `no_membership`. Waitlist promotions use the same check.
